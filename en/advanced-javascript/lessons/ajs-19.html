Custom Errors and Handling Strategies

Design clear error types with the original cause, and decide where to catch errors.

Open the interactive lesson (editor + quiz + progress)The exercise, quiz and progress tracking run on the interactive page.

Custom Errors

Extend Error and set name and additional properties. Use the cause option to keep the original error when wrapping it.

Where Do We Catch?

Catch the error where you can do something useful with it (retry, a message to the user); otherwise let it bubble up. Do not swallow errors silently.

Add context when rethrowing instead of hiding the original error.

Code example

JavaScript code

class ValidationError extends Error {
constructor(field, message, options) {
super(message, options);
this.name = "ValidationError";
this.field = field;
}
}
function parseAge(input) {
const n = Number(input);
if (!Number.isInteger(n) || n < 0) {
throw new ValidationError("age", "invalid age: " + input);
}
return n;
}
function load(input) {
try { return parseAge(input); }
catch (e) { throw new Error("load failed", { cause: e }); }
}
try { load("abc"); }
catch (e) {
console.log(e.message, "|", e.cause.name, e.cause.field);
console.log(e instanceof Error, e.cause instanceof ValidationError);
}
console.log(load("42"));
load failed | ValidationError age
true true
42

Understanding the code

The wrapped error keeps the original cause in cause, making it easier to trace. instanceof lets you distinguish between types inside catch.

Test yourself

  1. What is the purpose of the cause option?

    • Preserving the original error when rethrowing
    • Stopping the program
    • Converting the error to a string
    • Ignoring the error
    Answer and explanation

    Correct answer: Preserving the original error when rethrowing

  2. What is the best place to catch an error?

    • Where you can handle it usefully
    • On every line
    • Always in the global scope only
    • Never catch it
    Answer and explanation

    Correct answer: Where you can handle it usefully

  3. Why do we define custom error types?

    • To distinguish them with instanceof and attach data
    • To speed up the code
    • Because they are mandatory
    • To hide messages
    Answer and explanation

    Correct answer: To distinguish them with instanceof and attach data

  4. What does this code print? class MyErr extends Error { constructor(m) { super(m); this.name = "MyErr"; } } const e = new MyErr("x"); console.log(e instanceof Error, String(e));

    • false and Error: x
    • true and Error: x
    • true and MyErr: x
    • true and x
    Answer and explanation

    Correct answer: true and MyErr: x

    The class extends Error so it is an instanceof Error, and String uses name and message to give MyErr: x. Without setting name it would show Error: x.

  5. Which approach is best in a catch block when you do not recognize the error type?

    • Swallow it with an empty catch so the program does not stop
    • Check the type with instanceof, handle the known ones and rethrow the unknown ones
    • Turn every error into a generic text message
    • Only log it and carry on as if nothing happened
    Answer and explanation

    Correct answer: Check the type with instanceof, handle the known ones and rethrow the unknown ones

    Handle the errors you understand and can recover from, and rethrow the rest so a higher level can deal with them. Swallowing hides real bugs and makes them hard to find.
