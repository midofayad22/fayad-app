Final Project: The Complete FAY Language

Open the interactive lesson (editor + quiz + progress)The exercise, quiz and progress tracking run on the interactive page.

FINAL PROJECT

Source → Tokenizer → Parser → AST → Interpreter → Output

Learning objectives

  • Understand how the five stages connect and what passes between them.
  • Read a complete interpreter of about 90 lines and know the role of each part.
  • Add a new feature (the print command) through the stages concerned.

Prerequisites

  • Lessons 25 to 30 of this section.

The FAY language: what does it support?

  • Integers and decimals: 42 and 3.5.
  • The operators + - * / %, brackets and unary minus -x.
  • Variables: let price = 20.
  • Statements separated by newlines or ;.
  • And at the end of the project: the print command (you add it).

Stage 1: the tokenizer

One regular expression with alternative groups splits the text: whitespace (skipped), numbers, names, line breaks, operators, and anything else is an error. We store each token's position for error messages.

Stage 2: the parser

The same style you learned: one function per rule. We added program and statement above expression, term and factor, and an expect function for error messages. Notice that print is not there yet: that is your exercise.

Stage 3: the interpreter

How do you add a new feature?

To add print, ask at every stage: does the tokenizer know the word? (Yes: it is an ordinary id, so no change.) Does the parser know the shape of the statement? (No: add a branch in statement that produces {kind:"print", value}.) Does the interpreter know its meaning? (No: add a branch that appends the result to output.) This is the most important lesson: every feature passes through only the stages it affects.

Projects to continue after the exercise

  1. Add # comments (tokenizer only).
  2. Add a power operator ^ with higher precedence than multiplication.
  3. Add a simple if that compares two values.
  4. Improve the error messages to show the line and column.

Common mistakes

  • Adding the feature to the interpreter only and expecting it to work.
  • Changing the code without testing both valid and invalid inputs.
Exercise Why do we not need to change the tokenizer when adding print?
Show solution

Because print is made of letters the tokenizer already produces as an ordinary name (id). Recognising it as a special word happens in the parser, when it sees an id whose value is print at the start of a statement.

Summary

  • You built a complete interpreter: Source, Tokenizer, Parser, AST, Interpreter, Output.
  • Each stage is responsible for one thing and hands over a different shape of data.
  • A new feature passes through only the affected stages.

Core idea

A language is a pipeline of small stages, and every feature passes through the stages it affects.

Worked example

See the idea in code

JavaScript 
// the whole pipeline in one line (the functions come from the lesson)
const tokens = "let a = 2 + 3".match(/[A-Za-z_]\w*|\d+|[-+*/%()=]/g);
console.log(tokens);
Practice

Challenge yourself

Interactive exercise

The interpreter in front of you works but does not know the print command. Add it so that runFay("let a = 2\nlet b = a * 5\nprint b + 1") returns ["11"], while errors keep working (undefined variable, incomplete expression).

Test yourself

  1. What is the correct order of the stages?

    • Tokenizer, then parser, then interpreter
    • Interpreter, then parser, then tokenizer
    • Parser, then tokenizer, then interpreter
    • There is no order
    Answer and explanation

    Correct answer: Tokenizer, then parser, then interpreter

    Each stage takes the output of the one before.

  2. Which stage knows that print is a special statement?

    • The parser
    • The tokenizer
    • The screen
    • None
    Answer and explanation

    Correct answer: The parser

    It sees an id with the value print at the start of a statement and produces a print node.

  3. To add # comments, which stage changes?

    • The tokenizer
    • The interpreter
    • Only the parser
    • All three
    Answer and explanation

    Correct answer: The tokenizer

    A comment is dropped before the parser sees any token.

  4. Why do we store each token's position?

    • For precise error messages
    • To speed up the screen
    • To reduce memory
    • No need
    Answer and explanation

    Correct answer: For precise error messages

    The parser names the position of the offending token.

  5. You want FAY to support negative numbers like -5 + 2, and the lexer already produces the - token. Where is the minimal change?

    • The lexer, by adding a new token for negation
    • The interpreter only, not the parser
    • The parser (factor): if a factor starts with -, read the next factor and produce a negation node
    • No change is needed
    Answer and explanation

    Correct answer: The parser (factor): if a factor starts with -, read the next factor and produce a negation node

    The token already exists; the problem is that the grammar does not accept - at the start of a factor, so the change belongs in the parser rules (and the interpreter then evaluates the negation node). Changing the lexer would not add a grammar rule.
