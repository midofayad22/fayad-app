DEBUGGING

How a language detects a mistake and how you trace its source

Learning objectives

  • Tell lexical, syntax and runtime errors apart.
  • Understand how the parser detects an error and names its position.
  • Trace a problem by inspecting the output of each stage.

Prerequisites

  • The tokenizer and parser lessons (prg-26, prg-27) and the Debugging lesson (prg-17).

Three kinds of errors

Each stage of our interpreter sees the world in its own way, so it catches a different kind of problem. Knowing which stage rejected the code means you already have half of the answer.

LexicalTokenizer3 $ 4Unexpected character '$' at 2

RuntimeInterpreterprint y with no y definedUndefined variable 'y'

How does the parser detect an error?

The parser expects a particular token at every position. The expect function checks the next token: if it is the one expected it continues, otherwise it throws an error naming what it expected and where. Parsing (1 + 2 goes like this:

A systematic way to trace a problem

  1. Print the tokens: was the text split as you expected? If not, the problem is in the tokenizer.
  2. Print the tree with JSON.stringify(ast): does its shape match what you meant? If not, the problem is in the parser.
  3. Trace the evaluation: if the tree is right but the result is wrong, the problem is in the interpreter.

Common mistakes

  • Changing the interpreter to cure a bug caused by the parser: you fix the symptom, not the cause.
  • Generic error messages such as “Error” with no position or expectation, which cost hours of searching.
Exercise Which stage catches let = 5, and what is a suitable message?
Show solution

The parser: after let it expects a name and finds =. A suitable message: Expected a name after 'let'.

Summary

  • Each stage has its own kind of error.
  • A good message names what was expected and the position.
  • Trace a problem by inspecting each stage's output in order.

Next step: Now we actually run the tree: the interpreter and variables.

Core idea

Know which stage rejected the code and inspect each stage's output in order instead of guessing.

Worked example

See the idea in code

JavaScript 
const tokens = ["(", "1", "+", "2"];
let depth = 0;
for (const t of tokens) {
if (t === "(") depth++;
if (t === ")") depth--;
}
console.log(depth === 0 ? "balanced" : "unbalanced by " + depth);

Test yourself

  1. Which stage detects the unknown character $?

    • The tokenizer
    • The parser
    • The interpreter
    • None
    Answer and explanation

    Correct answer: The tokenizer

    A lexical error appears while splitting characters.

  2. What causes the message Expected ')' at the end?

    • An opening bracket with no closing one
    • An unknown character
    • Division by zero
    • An undefined variable
    Answer and explanation

    Correct answer: An opening bracket with no closing one

    The parser reached the end of the tokens while waiting for ).

  3. The tree is right but the result is wrong. Where do you look?

    • In the interpreter
    • In the tokenizer
    • In the keyboard
    • In the screen
    Answer and explanation

    Correct answer: In the interpreter

    The tree is the boundary between the parser and the interpreter.

  4. Why name the position in an error message?

    • So the user can reach the problem quickly
    • To decorate the message
    • To slow the program
    • No reason
    Answer and explanation

    Correct answer: So the user can reach the problem quickly

    Specific information saves searching time.

  5. Your calculator gives a wrong result for an expression and you do not know which stage is to blame. What is the best way to find out?

    • Print each stage's output in order (tokens, then tree, then result) and find the first place that differs from what you expect
    • Rewrite all three stages together
    • Change the expression until it works
    • Always look only in the last stage
    Answer and explanation

    Correct answer: Print each stage's output in order (tokens, then tree, then result) and find the first place that differs from what you expect

    Each stage takes the previous stage's output, so the first stage whose output is wrong is the culprit. Checking only the end can mislead you because the bug may start earlier.
