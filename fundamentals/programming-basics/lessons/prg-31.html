الدرس 31 من 31

المشروع النهائي: لغة FAY كاملة

افتح الدرس التفاعلي (محرر + اختبار + تتبّع التقدم)يعمل التمرين والاختبار وحفظ التقدم في الصفحة التفاعلية.

FINAL PROJECT

Source ← Tokenizer ← Parser ← AST ← Interpreter ← Output

أهداف الدرس

  • تفهم كيف تتصل المراحل الخمس وما الذي ينتقل بينها.
  • تقرأ مفسّرًا كاملًا بحوالي 90 سطرًا وتعرف دور كل جزء.
  • تضيف ميزة جديدة (الأمر print) عبر المراحل المعنية.

المتطلبات السابقة

  • الدروس 25 إلى 30 من هذا القسم.

لغة FAY: ما الذي تدعمه؟

  • أعداد صحيحة وعشرية: 42 و3.5.
  • العوامل + - * / % والأقواس والسالب -x.
  • المتغيرات: let price = 20.
  • عبارة تفصل بين الأسطر أو بـ ;.
  • وفي نهاية المشروع: الأمر print (ستضيفه أنت).

المرحلة 1: الـ Tokenizer

تعبير نمطي واحد بأجزاء بديلة يقسم النص: مسافات (تُهمل)، أعداد، أسماء، فواصل الأسطر، عوامل، وأي شيء آخر هو خطأ. نخزّن موضع كل Token لرسائل الخطأ.

المرحلة 2: الـ Parser

نفس الأسلوب الذي تعلمته: دالة لكل قاعدة. أضفنا program وstatement فوق expression وterm وfactor، ودالة expect لرسائل الخطأ. لاحظ أن print غير موجودة بعد: هذا هو تمرينك.

المرحلة 3: الـ Interpreter

كيف تضيف ميزة جديدة؟

لإضافة print اسأل في كل مرحلة: هل يعرف الـ Tokenizer الكلمة؟ (نعم: هي اسم عادي id فلا تغيير). هل يعرف الـ Parser شكل العبارة؟ (لا: أضف فرعًا في statement ينتج {kind:"print", value}). هل يعرف الـ Interpreter معناها؟ (لا: أضف فرعًا يضيف النتيجة إلى output). هذا هو الدرس الأهم: كل ميزة تمر على المراحل التي تتأثر بها فقط.

الميزةTokenizerParserInterpreter
عامل جديد ^يعرف الرمزقاعدة جديدةحالة جديدة
أمر printلا تغييرفرع في statementفرع في الحلقة
تعليق #يتجاهل حتى نهاية السطرلا تغييرلا تغيير

مشاريع تطوير بعد التمرين

  1. أضف التعليقات # (Tokenizer فقط).
  2. أضف عامل القوة ^ بأولوية أعلى من الضرب.
  3. أضف if بسيطة تقارن بين قيمتين.
  4. حسّن رسائل الخطأ لتعرض السطر ورقم العمود.

أخطاء شائعة

  • إضافة الميزة في الـ Interpreter فقط وانتظار أن تعمل.
  • تعديل الكود دون اختبار بمدخلات صحيحة ومدخلات خاطئة معًا.
تمرين لماذا لا نحتاج إلى تعديل الـ Tokenizer عند إضافة print؟
عرض الحل

لأن print تتكوّن من أحرف ينتجها الـ Tokenizer أصلًا كاسم عادي (id). تمييزها ككلمة خاصة يتم في الـ Parser عندما يرى id قيمته print في بداية عبارة.

الخلاصة

  • بنيت مفسّرًا كاملًا: Source ← Tokenizer ← Parser ← AST ← Interpreter ← Output.
  • كل مرحلة مسؤولة عن شيء واحد وتسلّم شكلًا مختلفًا من البيانات.
  • الميزة الجديدة تمر على المراحل المتأثرة فقط.

الخطوة التالية: راجع الدروس 21 إلى 31 ثم جرّب الاختبار النهائي للمسار.

الفكرة الأساسية

اللغة هي خط أنابيب من مراحل صغيرة، وكل ميزة تمر على المراحل التي تتأثر بها.

تمرين تفاعلي

المفسّر أمامك يعمل لكنه لا يعرف الأمر print. أضفه بحيث يعيد runFay("let a = 2\nlet b = a * 5\nprint b + 1") المصفوفة ["11"]، مع بقاء الأخطاء كما هي (متغير غير معرّف، تعبير ناقص).

اختبر نفسك

  1. ما الترتيب الصحيح للمراحل؟

    • Tokenizer ثم Parser ثم Interpreter
    • Interpreter ثم Parser ثم Tokenizer
    • Parser ثم Tokenizer ثم Interpreter
    • لا يوجد ترتيب

    • الـ Parser
    • الـ Tokenizer
    • الشاشة
    • لا أحد

    يرى id بقيمة print في بداية العبارة فينتج عقدة print.

  3. لإضافة تعليقات # أي مرحلة تتغير فقط؟

    • الـ Tokenizer
    • الـ Interpreter
    • الـ Parser فقط

    الإجابة الصحيحة: الـ Tokenizer

    التعليق يُهمل قبل أن يرى الـ Parser أي رمز.

  4. لماذا نخزّن موضع كل Token؟

    • لرسائل خطأ دقيقة
    • لتسريع الشاشة
    • لتقليل الذاكرة
    • لا حاجة
    الإجابة والشرح

    الإجابة الصحيحة: لرسائل خطأ دقيقة

    الـ Parser يذكر موضع الرمز المسبب للخطأ.

  5. تريد أن تدعم FAY الرقم السالب مثل -5 + 2 والرمز - يُنتجه المحلل المعجمي فعلاً. أين التعديل الأدنى؟

    • المحلل المعجمي، بإضافة رمز جديد للسالب
    • المفسّر فقط دون المحلل النحوي
    • المحلل النحوي (factor): إذا بدأ العامل بـ - فاقرأ العامل التالي وأنتج عقدة سالب
    • لا حاجة لأي تعديل
    الإجابة والشرح

    الإجابة الصحيحة: المحلل النحوي (factor): إذا بدأ العامل بـ - فاقرأ العامل التالي وأنتج عقدة سالب

    الرمز موجود أصلاً، والمشكلة أن القواعد لا تقبل - في بداية العامل، فالتعديل في قواعد الـ parser (ثم يُقيِّم المفسّر عقدة السالب). تعديل المحلل المعجمي لا يضيف قاعدة نحوية.
